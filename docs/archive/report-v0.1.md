# 技术报告：JobSkill-KG 中文 IT/算法岗位—技能知识图谱

> 课程设计成果｜2026-11｜数据与代码见 `jobskill-kg/`｜OpenKG 发布物见 `jobskill-kg/deliverable/`

---

## 1. 选题与目标

招聘文本是典型的开放域中文文本：岗位职责与任职要求写成自由段落，技能、学历、经验、薪资都埋在句子里。
本题从**企业官方招聘站的公开岗位信息**出发，抽取岗位—技能关系，构建可查询、可分析的岗位技能知识图谱，并发布到 OpenKG。

- 范围：算法、数据、后端、前端客户端、测试、运维安全、MLOps 七个 IT 岗位族
- 目标：不做"百科搬运"，而是**必须靠抽取才能得到**的结构化知识

## 2. 数据

| 来源 | 原始岗位 | 说明 |
|---|---|---|
| 字节跳动招聘 | 10,000 | 官方招聘站公开接口 |

筛选口径（详见 `docs/data_sources.md`）：站点岗位大类排除产品/设计/市场/运营，标题强技术信号例外保留，正文 <40 字丢弃，按内容哈希去重。

**岗位族分布**（进入图谱的 4,865 条）：算法 2,193｜后端 870｜前端客户端 743｜运维安全 414｜数据 405｜测试 215｜MLOps 25。

合规：只抓公开页面、限速 ≥0.3s、保留来源 URL 与抓取时间、**原始 JD 不对外分发**。

## 3. 方法

### 3.1 技能抽取：词典 + 序列标注两路

| 方法 | 做法 | 特点 |
|---|---|---|
| **词典匹配** | 人工整理 410 条技术词表（语言/框架/工具/算法/通用能力），字符级 Trie 最长匹配 | 精确率高（量表词），召回受词表限制 |
| **序列标注** | 在 Chinese-SkillSpan（4,731 句、12,856 个 gold span）上微调 bert-base-chinese，字符级 BIO，4 类标签（K/S/T/L） | 召回高，但边界噪声大 |

模型配置：batch 16、max_len 96、lr 3e-5、AdamW、MPS 加速；训练集用官方 dev 划分（2,141 句），测试集用 test 划分（2,590 句）。

### 3.2 融合与后处理

- 词典命中置信度 0.98；模型 span 取平均 softmax 概率，低于 0.85 丢弃
- 裁掉 span 两端的虚词（的/和/及/与/等/或/并/其/了/着/对/把/为/以/用/途），长度限定 2–20 字
- 按上下文 8 字窗口推断「掌握程度」（了解/熟悉/精通）与「必要性」（必备/加分）

### 3.3 归一化

别名词表 + 小写/标点归一：NLP→自然语言处理、K8s→Kubernetes、js→JavaScript、大模型/LLM→大语言模型…
归一后技能词条 389 个，分 12 类；长尾仍靠扩表增长，见 §7。

## 4. Schema：cnSchema 扩展

复用 9 个 cnSchema/schema.org 词汇（JobPosting、Organization、Place、MonetaryAmount 等），新增 18 个（5 个类 + 13 个属性）：

| 类（5 个） | 用途 |
|---|---|
| `cns:Skill` | 技能实体，承载类型/等级/必要性 |
| `cns:SkillCategory` | 技能分类树（12 类） |
| `cns:JobFamily` | 岗位族（7 族） |
| `cns:SalaryRange` | 薪酬区间 + 薪数 |
| `cns:JobRequirement` | 学历/经验等硬性条件 |

| 属性（13 个） | domain → range |
|---|---|
| `cns:requiresSkill`、`cns:belongsToFamily`、`cns:hasSalaryRange`、`cns:inCategory` | 4 个对象属性，串起岗位—技能—分类 |
| `cns:skillType`、`cns:proficiency`、`cns:necessity`、`cns:escoCode` | 技能自身的类型/等级/必要性/ESCO 对齐 |
| `cns:educationLevel`、`cns:experienceYears` | 岗位的学历与经验要求 |
| `cns:monthlyMin`、`cns:monthlyMax`、`cns:salaryMonths` | 薪酬区间的三个数值字段 |

本体文件：`schema/cns_jobskill.ttl`（110 条三元组，rdflib 校验通过）、`schema/context.jsonld`。

## 6. 应用

单文件静态站点 `app/site/index.html`（1.8 MB，双击即开，无需服务器），五个功能页签（另有「关于数据」说明页）：

1. **岗位族画像**：选族 → 高频技能 Top20 条形图
2. **技能检索岗位**：多选技能（AND）+ 城市 + 岗位族 → 岗位列表（含原文链接）
3. **技能差距分析**：选目标族 + 勾选已掌握技能 → 缺哪些必备技能、按需求频次排序
4. **技能分类**：12 个 `SkillCategory` 的卡片视图，点击可查该分类下的技能与需求频次
5. **智能问答**：中文提问，规则解析城市/岗位族/技能，答案附证据岗位

### 6.1 查询 API

配套一个标准库实现的 Restful 服务 `src/app/serve_api.py`（对应 OpenKG「数据查询 API」要求）：

| 端点 | 作用 |
|---|---|
| `/api/stats` | 规模与分布 |
| `/api/skills?family=&q=` | 技能列表 |
| `/api/jobs?skills=&city=&family=&limit=` | 技能 AND 检索岗位 |
| `/api/gap?family=&have=` | 技能差距 |
| `/api/job/<doc_id>` | 单岗位详情 |

启动 `python3 src/app/serve_api.py` 即可，无需第三方依赖；接口文档见 `docs/api.md`。

## 7. 实验与评测

### 7.1 技能抽取（Chinese-SkillSpan test）

测试集：官方 test 划分 2,590 句、2,098 个 gold span。

| 指标 | 精确率 | 召回率 | F1 |
|---|---|---|---|
| Exact span | 0.245 | 0.406 | **0.306** |
| Relaxed（同标签重叠即命中） | 0.416 | 0.689 | **0.519** |

分标签 F1（exact）：T 0.494｜L 0.393｜K 0.296｜S 0.267。

> 说明：训练语料仅 2,141 句，模型 3 个 epoch 后训练 loss 已降到 0.03（明显过拟合），
> 泛化仍是主要瓶颈；给更多标注数据应能显著提升。

**错误类型**（抽样 20 条）：

| 类型 | 例子 | 占比估计 |
|---|---|---|
| 边界错位 | `沟通能力` → `的沟通能` | 高 |
| 碎片化 | `回收并分析各平台数据` → `回收`+`分析` | 高 |
| 类型混淆 | `智慧校园` 标成 K（应为 S） | 中 |
| 长 span 截断 | `监控和管理…性能和容量` → 只取首词 | 中 |

### 7.2 域内评测（100 句，silver）

从 4,904 条岗位中抽 100 句（70 句含技能线索词、30 句随机），由 LLM 按 `docs/annotation_guideline.md`
独立标注（未经人工复核，故称 silver；复核脚本已备好，见 `eval/domain_review.jsonl`）。
词典抽取结果与之对比：

用这 100 句的错误分析反哺词表（补 39 个工具名词 + 修正 14 个领域名词的 K/S 类型），前后对比如下：

| 指标 | 扩词表前 | 扩词表后 |
|---|---|---|
| Exact P / R / F1 | 0.781 / 0.399 / 0.528 | **0.880 / 0.585 / 0.703** |
| Relaxed P / R / F1 | 0.854 / 0.436 / 0.578 | **0.904 / 0.601 / 0.722** |
| K 类 F1 | 0.526 | **0.813** |

召回从 0.40 提到 0.58，精确率反而从 0.78 升到 0.88——因为补进去的都是具体工具名
（vLLM、SGLang、Vespa、PagedAttention、NCCL、SerDes、Tool Calling），同时删掉了「开源」「编程语言」
这类过于泛化、会被到处命中的词。K 类大幅提升还因为把「机器学习/深度学习/大语言模型」等
**领域名词从 S 改判为 K**，与标注规范（K=知识/实体，S=可执行动作）对齐。

> ⚠️ 方法学提醒：这轮扩词表是**看着这 100 句的错误来补的**，属于在评测集上调参，上述提升有乐观偏差。
> 正式数字应在另抽的 100 句上复核（复核流程见 `docs/annotation_guideline.md` §8）。

**仍需承认的短板**：召回 0.58 意味着四成长尾技能仍抽不到，且 S 类 F1 只有 0.54——
中文技能片段的边界本来就模糊（"分析问题和解决问题的能力"该整段标还是拆开标），这是后续要解决的。

### 7.3 精度抽检（40 条）

在 4,904 条岗位里随机抽 40 条技能提及，逐条核对上下文：

| 结果 | 条数 | 说明 |
|---|---|---|
| 明确成立 | 37 | 如 Transformer、Paxos、微前端、跨团队协作 |
| 边界（岗位词/职责词） | 3 | 如"服务端"作岗位描述、"招聘数据分析" |
| **精度** | **0.925** | 与 §7.2 的 0.78–0.85 相互印证 |

### 7.4 融合策略对比

| 策略 | 精度 | 召回 | 取舍 |
|---|---|---|---|
| 词典 | 0.88（§7.2）、抽检 0.93 | 0.58（扩词表后），仍受词表限制 | **KG 采用** |
| 模型 | 边界噪声明显（exact F1 0.306） | 高（relaxed R 0.689） | 作为对照实验保留 |
| 词典 ∪ 模型 | 中 | 中 | 噪声进入三元组，未采用 |

**结论**：课程数据规模下，词典为主、模型为实验与后续扩展方向，是质量与成本的最优解。

## 8. 差异化

- OpenKG 410 个数据集中「招聘」「岗位」命中 **0**；「技能」只在 2 个娱乐图谱的简介里作为普通词出现，
  没有"岗位—技能"类数据集，本题填补这一空白
- 与既有课程作业（娱乐/动漫人物关系）相比，本题的实体来自**非结构化文本抽取**，不是百科结构化字段转存
- Schema 扩展有明确理由表，可回馈 cnSchema 社区

---

## 9. 局限与改进

1. **技能词表仍不够大**（410 条）：域内召回 0.59，长尾技能（新品名、内部平台名）覆盖不足，需持续扩表或半自动挖掘
2. **模型泛化弱**：2,141 句训练数据太少；可换更大中文预训练模型、加 CRF 层、或用 LLM 蒸馏标注
3. **无薪资字段**：三个来源都不公布薪资，`cns:SalaryRange` 已建模但暂为空，后续接入含薪资来源
4. **岗位族归类靠规则**：边界岗位（如「算法产品经理」）易误判，可训一个小分类器

「最少 1」说明抽取没有漏掉整个岗位，只是短 JD 本身技能就少；中位数 9 与人工直觉一致。

### A.2 技能频次的長尾

389 个技能中，出现 ≥100 次的有 116 个（头部集中），只出现 1 次的有 12 个。
长尾不长，说明词表覆盖的是"公共技能"，没有把公司内部平台名收进来——这是有意的。

### A.3 39 条"零技能"岗位是什么

| 类型 | 例子 | 原因 |

| 职能岗误入 | Talent Acquisition Partner、HRBP、Procurement Operations Manager、Global Communications Manager | 标题含 Data/AI 等词，触发了技术信号例外 |
| 英文 JD | Senior Cloud Infrastructure Architect、Frontend Engineer（日文） | 正文是英文/日文，中文词表命中不了 |
| 非软件硬件岗 | 图像传感器模拟设计专家、光互连工程师 | 模拟电路/光通信不在词表范围 |

占语料 0.8%，且都已排除在图谱外，不影响图谱质量；但说明**分类器对跨语言 JD 是盲区**。

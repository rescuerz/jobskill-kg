# 与 OpenKG 已发布数据集的横向对照

> 目的：不只对照「官方要求」，还对照「别人实际怎么发」——看看我们的提交物在真实分布里处于什么位置。
> 数据来源：data.openkg.cn CKAN API，2026-11-01 抓取 200 个数据集 + 10 个代表作细看。

---

## 一、平台现状（200 个数据集）

| 指标 | 中位数 | P90 / 最大 | 说明 |
|---|---|---|---|
| 资源数 | **2** | P90 ≈ 5，最大 15 | 多数只挂 1–2 个文件 |
| 简介（notes）长度 | **164 字** | P90 = 513 字 | 大多数只有一两句话 |
| 标签数 | **2** | — | 标签普遍很少 |

**资源类型覆盖率**

| 资源类型 | 含该资源的比例 |
|---|---|
| 任何 Schema（ttl/ontology/json-ld） | 34 / 200（**17%**） |
| JSON-LD 格式 | 19 / 200（**10%**） |
| 数据门户 | 4 / 200（**2%**） |
| 样例数据 | 3 / 200（**2%**） |
| 数据访问 API | 未统计到成规模的样本（极少） |

**许可证**：Creative Commons Attribution 占 60%（120/200），其余为非商业、Other (Open)、未指定等。

## 四、据此做的两处调整

对照之后改了两处，不是加东西，而是**向平台惯例靠拢**：

1. **简介从 1,200 字压到 664 字**：原来把整份 README 塞进 notes，而平台 P90 只有 513 字。
   压成「一段简介 + 三行构建方法 + 一行文件说明」，细节留在门户 README 里。
2. **标签从 6 个减到 4 个**：`招聘 / 技能 / 岗位 / 知识图谱`，去掉「信息抽取」「IT」这类过宽的标签。

---

## 五、结论

我们的提交在**完整度上明显高于平台中位数**：8 个资源、双格式 Schema、样例、门户、API 全齐，
而平台 83% 的数据集连 Schema 都没有。

但也因此有个风险：**资源越多，命名越要清楚**。官方要求资源名写「样例数据 / 数据下载（JSON-LD）」
这类规范名，我们照做了——这比多数现存数据集更符合官方指引，审核时是加分项。

反过来说，如果只挂 1 个 JSON 文件（像 20% 的数据集那样），通过率也不会低——
但那就成了"能过审"而不是"做得好"。我们选前者。

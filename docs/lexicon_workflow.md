# 词表维护工作流：发现 → 审核 → 验证

> 技能词表不是一次写完的。这份文档记录"怎么让它持续变好"，以及一次真实的取舍案例。

## 一、为什么要流程化

词典是我们图谱的主要抽取路径，词表覆盖率直接决定召回。但**手工想词表有两个坑**：
一是想不全（长尾工具名想不起来），二是想太多（把"开源""AI"这种泛化词也塞进去，精确率立刻掉）。

所以需要一条闭环：机器发现候选 → 人判断 → 评测验证。

## 二、三步

### 1. 发现：`src/extract/suggest_terms.py`

```bash
# 只看线索词挖掘（快，约 1 分钟）
PYTHONPATH=.pkgs python3 src/extract/suggest_terms.py --limit 1200 --min-count 15

# 叠加微调 BERT 的预测（慢，能发现不带"熟悉/掌握"的裸词）
PYTHONPATH=.pkgs python3 src/extract/suggest_terms.py --use-model --limit 400 --min-count 4
```

脚本做的事：
1. 线索词（熟悉/掌握/精通/使用…）+ 词性切分抽候选；可选叠加 BERT 预测
2. 用**当前词表**做 Trie 匹配，删掉已被覆盖的（只留缺口）
3. 过滤：岗位标题里的词（角色名不是技能）、泛化词、模型边界碎片（`I技术`、`C验证`）、
   无技术特征的长中文串
4. 按频次排序输出 `data/lexicon/suggested_terms.tsv`

### 2. 审核：人来判断两件事

| 判据 | 收 | 不收 |
|---|---|---|
| 是不是**具体**技能/工具/知识实体 | vLLM、SerDes、存算一体芯片 | 算法、网络、协议、平台 |
| 出现时**是否总是**技能 | 在"熟悉 X"里稳定出现 | "AI 产品/AI 能力"里 AI 只是修饰语 |

### 3. 验证：改完必须跑评测

```bash
PYTHONPATH=.pkgs python3 src/extract/eval_domain.py
```

对比扩表前后的 P / R / F1。**只看召回不看精确率是危险的**——下面就是反例。

## 三、一次真实的取舍：为什么拒收 "AI"

用 `--use-model` 跑 400 个岗位，候选里 "AI" 出现 21 次，看着很像个该收的通用技术词。加进去之后：

| 指标 | 加 AI 前 | 加 AI 后 |
|---|---|---|
| Exact P | 0.880 | **0.816** |
| Exact R | 0.585 | 0.590 |
| Exact F1 | 0.703 | **0.685** |

原因：JD 里 "AI" 大量出现在"AI 产品""AI 能力""AI 基础设施"里，是**修饰语**而不是被要求的技能；
gold 标注只在"了解 AI 前沿技术"这类句子里标了它。收进词表 → 满篇误报。

同一批候选里收了 10 个（存算一体芯片、人工智能芯片、交换芯片、网卡芯片、知识库、搜索引擎、
中间件、数据面 DPDK、ARM、SOC）——它们低频但精确，加进去对 100 句评测**没有影响**（那些句子没出现），
但让图谱多了 10 个真实存在的技能节点。

**结论：频次高 ≠ 该收；"总在技能位置出现"才该收。**
